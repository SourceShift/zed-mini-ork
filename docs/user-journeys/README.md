# Engineer journey graph

A capability-first map of what an engineer can actually accomplish with
mini-ork, and of the distance between the engine and the IDE that is supposed
to expose it.

The engine is the source of truth. Existing UI, UX briefs and docs are **not**
used as input: they describe what someone intended, and the gaps we are hunting
live precisely where intent and engine diverge. Every capability here is read
from the running engine at a recorded commit, and every journey is checked
against that inventory before it is published.

## Why a graph

| Construct | What it is | Where it comes from |
|---|---|---|
| `cli:<verb>[ <sub>]` | A command the dispatcher wires | `SUBCOMMAND_REGISTRY` + argparse trees + each command's own `--help` |
| `mcp:<tool>` | A tool an agent can call | `TOOL_DEFS` and `_CONTROL_TOOL_DEFS` in `mini_ork/mcp_context/server.py` |
| `knob:<id>` | A cost/behaviour feature toggle | `mini_ork.features.catalogue_json()` |
| page | One IDE page (`runs`, `run`, `verify`, …) | `PAGES` in `mini_ork/ide_pages/__init__.py` |
| action | A `S.cli(...)` path a page emits | AST walk of `mini_ork/ide_pages/*.py` |
| journey | An engineer's goal, composed of ≥2 capabilities | hand-authored, validated |

Edges: `journey → step` (order), `page -.-> step` (the page hosts the step's
button), and implicitly `step → capability` by id. A journey is only as
reachable as its worst step, because a goal that needs one shell-only command
is not a goal the IDE can deliver.

## Files

| File | Provenance |
|---|---|
| `capabilities.json` | generated by `script/mo-surface`; pins engine root, HEAD and version |
| `journeys/*.yaml` | hand-authored corpus, one file per persona |
| `graph.md` | generated by `script/mo-journeys` (Mermaid, one diagram per persona) |
| `gaps.md` | generated by `script/mo-journeys` (reach, uncovered capabilities, help hazards) |

## Running it

```bash
./script/mo-surface     # inventory the engine → capabilities.json
./script/mo-journeys    # validate corpus → graph.md, gaps.md
```

Both re-exec themselves under the engine's virtualenv because only that
interpreter can import `mini_ork`. Override discovery with `--engine <path>` or
`MINI_ORK_ENGINE`. `mo-journeys` exits non-zero when the corpus cites a
capability, page or terminal anchor the engine does not have — those are corpus
bugs, not product findings, and must not be published as gaps.

## Journey schema

```yaml
journeys:
  - id: persona/goal-slug          # unique, `persona/` prefix
    persona: debugger
    value: "one sentence: the outcome the engineer gets"
    impact: "one sentence: why the outcome matters"
    preconditions:
      - "state the machine must already be in"
    steps:
      - cap: cli:board retry       # must exist in capabilities.json
        page: run                  # optional; must be a PAGES key
        note: "why this step, not the near-miss alternative"
    terminal_evidence:
      kind: git | file | dir | db-row | run-row
      anchor: "retry-hint.json"    # literal the engine must contain
```

`value` is the acceptance test for a journey: if it does not name a goal with
impact, the journey is a task list and should be merged into another one.

## Reach semantics

`full` — the exact verb path is emitted by a page.
`partial` — only a parent command or a path prefix of it is emitted; the page
exists but does not offer this step.
`none` — no page emits anything that runs this step.

Known limits, all of which understate reach rather than overstate it:

- **MCP tools score `none` by construction.** Agents reach them, the IDE has no
  button for them. That is the finding, not a measurement error.
- `S.cli(*argv)` (2 call sites) cannot be resolved statically and is reported as
  dynamic.
- ACP slash commands are not enumerated; they are an agent surface with no
  page action.
- A `partial` match means "some sibling subcommand is exposed"; it does not
  prove the page's button has the arguments this journey needs.
- `--help` subcommand extraction is textual for the 56 commands with
  hand-written help (26 have argparse trees). It is deliberately conservative
  (prose is rejected), so a miss is possible; the inventory's `parser` field
  records which source a command's subcommands came from.

## Gap taxonomy

| Class | Meaning | Pilot evidence |
|---|---|---|
| hidden | wired in the dispatcher but absent from `mini-ork --help` | 50 commands, 77 subcommands |
| unreachable | no page action emits the verb | 194 of 255 CLI capabilities |
| half-exposed | a page exists but lacks the step (`partial`) | 32 CLI capabilities |
| undiscoverable help | `--help` crashes, prints usage-only, or runs the command | 14 commands (1 crash, 4 usage-only, 9 executed) |
| agent-only | reachable only from an MCP client | all 19 MCP tools |

## Pilot results (15 journeys)

Engine `mini_ork` 0.9.0 at `8d792bcc`:

- 82 commands, 173 subcommands, 9 knobs, 19 MCP tools.
- Pages emit 46 distinct action paths.
- 29 CLI capabilities reachable exactly, 32 partially, 194 not at all.
- 0 MCP tools exposed in the IDE.
- The 15 journeys cite 55 of 283 capabilities; none is runnable end-to-end from
  the IDE.

The four most valuable missing surfaces the pilot already names:

1. Onboarding (`onboard`, `init`, `zed setup`, `validate`) has no page action at
   all, while `setup` is a page key.
2. Spend and lifetime reporting (`lifetime summary|show`, `usage-report`) is
   shell-only; only `usage-report` has a button, from the lanes page.
3. Failure forensics (`reap`, `supervise`, `repair`, `verifier annotate`,
   `graph-patch propose|apply`) is invisible to the IDE even though the `run`
   and `verify` pages exist to show failures.
4. Authoring (`kickoff new`, `mcp:draft_kickoff`, `mcp:draft_recipe`,
   `mcp:propose_automation`) is agent-only: a human cannot see or approve a
   draft the agent produced from inside the IDE.

## Scaling to the full corpus

The 200-journey floor is a coverage requirement, not a count of ideas. Grow it
persona by persona, each iteration:

1. pick the persona with the most uncovered capabilities in `gaps.md`;
2. group uncovered capabilities into goals that already have a caller in
   `mini_ork/` (a page, a scheduled entry point, or a documented workflow);
3. add journeys, re-run `./script/mo-journeys`, and stop when the
   "capabilities with no journey" lists are empty or every remaining entry has
   a written reason for being unjourneyable (pure internals, eval harnesses).

Re-run `./script/mo-surface` whenever the engine HEAD moves; a stale
`capabilities.json` silently pins the corpus to an old product.
